PHASE 6 — IMPLEMENT THE AUTHORITATIVE ESTIMATION ENGINE
==================================================

Create one authoritative backend estimation service.

Suggested file:

backend/app/services/estimation/engine.py

All estimates, recalculations, comparisons and what-if scenarios must use this service.

Do not maintain separate competing estimation formulas in the frontend, dashboard, API, comparison module and analytics module.

Implement this calculation sequence:

1. Validate project inputs.
2. Validate features and identifiers.
3. Validate dependencies.
4. Calculate dependency graph properties.
5. Calculate feature complexity.
6. Obtain feature-level O/M/P effort.
7. Apply justified integration adjustments.
8. Apply platform adjustment only to the relevant client-side effort.
9. Add fixed project-level work not already included in feature estimates.
10. Calculate expected total effort.
11. Reconcile the project-level ML prediction with feature-level totals.
12. Allocate effort by role.
13. Calculate staffing and available capacity.
14. Calculate team scaling and coordination adjustments if supported.
15. Calculate the critical path.
16. Calculate timeline feasibility.
17. Calculate uncertainty and contingency.
18. Calculate role-based labour costs.
19. Add applicable infrastructure, tools and other direct costs.
20. Calculate the final budget range.
21. Calculate risk and confidence using documented rules.
22. Generate recommendations and assumptions.
23. Return the structured estimate and its version metadata.

THREE-POINT ESTIMATION:

For each work item, use:

ExpectedHours = (Optimistic + 4 × MostLikely + Pessimistic) / 6

StandardDeviation = (Pessimistic - Optimistic) / 6

Apply this to features and fixed project work whenever O/M/P inputs are available.

Fixed work may include:

- Kickoff and requirements.
- Architecture.
- Repository setup.
- Environment setup.
- CI/CD.
- Deployment.
- Documentation.
- Basic monitoring.

Only include work not already covered by feature estimates.

Use a documented correlation adjustment for project-level uncertainty if the statistical assumptions justify it.

Do not invent statistically calibrated confidence intervals from unsupported percentages.

Do not blindly multiply every feature by every complexity, platform, integration and risk multiplier. This would inflate costs by repeatedly counting the same work.

PLATFORM ADJUSTMENT:

Use configurable platform multipliers, but apply them only to the appropriate client-side portion of feature effort.

AdjustedEffort = BackendEffort + (ClientEffort × PlatformMultiplier)

Do not multiply the entire backend effort by the number of platforms.

If the dataset does not provide a reliable client/backend split, use a documented configurable assumption and disclose it.

EFFORT RECONCILIATION:

The project-level ML model and feature-level estimator must not be added together as two complete estimates.

Compare their outputs and use a documented reconciliation strategy.

Default strategy:

- Feature-level estimates provide the primary explainable breakdown.
- The project-level model provides a cross-check and contextual benchmark.
- A calibrated combination may be used only if validated on held-out data.

If predictions differ substantially, display a warning, identify the discrepancy and explain that the estimate requires review.

Do not silently force the outputs to match.

PHASE 8 — COST ENGINE AND BUDGET RANGE
==================================================

Use configurable role-specific hourly rates.

Provide rate profiles such as:

- Startup.
- Professional.
- Enterprise.
- Custom.

The current workbook's rates are simulated estimates, not verified market rates. Label them accordingly.

Allow users to edit rates and show the source or status of each rate.

ROLE COST:

RoleCost = AllocatedRoleHours × RoleHourlyRate

LABOUR COST:

TotalLabourCost = Sum(RoleCost)

ADDITIONAL COSTS:

Track separately:

- One-time infrastructure setup.
- Software and development tools.
- Other direct project expenses.
- Recurring hosting, if explicitly included.
- Ongoing maintenance, if explicitly included.
- Taxes, if explicitly included.

Do not include recurring hosting or maintenance in a one-time build estimate unless the user explicitly requests it.

PRE-CONTINGENCY COST:

PreContingencyCost = TotalLabourCost + OneTimeInfrastructure + Tools + OtherDirectCosts

CONTINGENCY:

ContingencyAmount = PreContingencyCost × ContingencyRate

FINAL BUILD BUDGET:

FinalBudget = PreContingencyCost + ContingencyAmount

Ensure that contingency is not added twice.

If the selected target already includes contingency, do not add it again.

For an uncertainty-aware estimate, calculate low, likely and high values consistently. Use O/M/P effort and a documented uncertainty method where the inputs justify it.

The headline budget should be a range where appropriate, not a falsely precise guaranteed quotation.

For the cost range, maintain consistency between effort, role allocations and rates.

If fixed rates are used:

CostLow = LowEffort × BlendedRate

CostLikely = ExpectedEffort × BlendedRate

CostHigh = HighEffort × BlendedRate

Use this shortcut only when the blended rate is genuinely appropriate. Otherwise, calculate each range using role-specific hours and rates.

Contingency must be included exactly once.

Do not add feature costs to role costs when feature costs are merely a breakdown of the same labour.

MANDATORY FINANCIAL INVARIANT:

ReportedBuildLabourCost must equal:

Sum(RoleHours × RoleHourlyRate)

within a defined numerical tolerance.

Infrastructure, maintenance and other direct costs must remain separately visible.

Use INR as the default currency.

Retain full precision internally and round only for display.
